# Day 05: CUDA Timing and Performance Baseline

## Objective

Establish a reproducible kernel-only performance measurement for the Day 04 vector-add kernel.

## Why timing matters

A GPU workload has multiple costs. Host-to-device transfer, kernel execution, and device-to-host transfer should not be collapsed into one number when studying kernel performance.

Day 05 therefore uses CUDA events around repeated kernel launches after warm-up.

## Measurement

The benchmark uses:

- 16,777,216 elements
- float32 inputs
- 256 threads per block
- 65,536 blocks
- 10 warm-up launches
- 100 measured launches

CUDA events measure elapsed time on the GPU timeline.

The benchmark reports:

- configuration
- average kernel execution time
- estimated effective memory bandwidth

For vector addition, the bandwidth estimate uses three float arrays, two reads and one write:

`bytes moved = 3 * N * sizeof(float)`

`effective bandwidth = bytes moved / kernel time`

This is an effective bandwidth metric, not a claim about the GPU's theoretical peak bandwidth.

## Experimental discipline

1. Allocate device buffers.
2. Copy inputs to the GPU.
3. Warm up the kernel.
4. Synchronize.
5. Record a CUDA event.
6. Run many kernel iterations.
7. Record the stop event.
8. Synchronize on the stop event.
9. Calculate average kernel time.
10. Copy output back and validate it.

This separates launch and initialization effects from the steady-state kernel measurement.

## What the benchmark does not measure

It does not represent end-to-end application latency. PCIe or other host-device transfer time is excluded from the reported kernel timing.

It also does not prove that 256 threads per block is optimal. That configuration is the baseline for later experiments.

## Next experiments

Compare several block sizes, measure kernel timing across input sizes, and inspect whether the operation approaches a memory-bandwidth limit. Keep one variable changing per experiment.
