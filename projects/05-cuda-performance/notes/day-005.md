# Day 05: CUDA Block-Size Experiment

Day 5 moves performance benchmarking into Project 05, as a separate project from the kernel implementation work in Project 04.

## Hypothesis

Vector addition has low arithmetic intensity and predictable contiguous memory access. Block size should affect launch configuration and scheduling, while the dominant cost for a sufficiently large workload is expected to remain global-memory traffic.

This is an experimental hypothesis, not a measured conclusion until the benchmark runs on a specific GPU.

## Controlled variables

The benchmark fixes:

- 16,777,216 elements
- float32 data
- vector-add operation
- 10 warm-up launches
- 100 measured launches

Only threads per block changes.

## Configurations

```text
64 threads/block
128 threads/block
256 threads/block
512 threads/block
```

## Why CUDA events

GPU kernels execute asynchronously relative to the host. CUDA events provide timing on the GPU execution timeline and avoid treating host-side launch overhead as kernel execution time.

## Effective bandwidth

Each element requires two reads and one write. The benchmark therefore estimates:

`3 * N * sizeof(float) / kernel_time`

The metric helps compare configurations for the same operation. It does not measure total application throughput or theoretical peak bandwidth.

## What to record on real hardware

- GPU model
- compute capability
- driver version
- CUDA toolkit version
- compiler version
- input size
- block size
- kernel latency
- effective bandwidth

## Expected analysis

The useful result is not simply the fastest configuration. The goal is to connect a performance change to a CUDA mechanism such as occupancy, scheduling, memory behavior, or launch characteristics.
